## 5. What matters most

These are the findings that change what a reader sees most often. Each maps to proposals in `A1-appendix-cps.md`, where they can be found by selector.

1. **Square brackets take the member colour** in C and everything else that uses `bracket.square` scopes. The Members rule lists them (selector `punctuation.definition.begin.bracket.square`).
2. **Rust type keywords and `let` show the primitive-type colour** without rust-analyzer: `storage.type.rust` wins over `keyword.declaration.*`. Under P1 they become keywords, which is also what rust-analyzer already sends (selector `storage.type.rust`).
3. **Rust `u8`, `usize`, `str` show the user-type colour** without rust-analyzer; numeric suffixes too. rust-analyzer gets them right (`builtinType`), so the modes split.
4. **cpptools renders `uint8_t` and `size_t` in the user-type colour** (`type`, no library modifier). clangd marks them `defaultLibrary`, which Rosin maps to primitive. That's your turquoise: correct under clangd, a cpptools limit, and the README example was wrong either way.
5. **Kconfig keywords show the hazard colour**: the ESP-IDF grammar uses `variable.language.kconfig`, which Rosin maps to hazard.
6. **Devicetree node and label rules are reversed** for this grammar, and **ARM registers and labels are plain**: the grammar's scope names aren't covered.
7. **Make and CMake variable delimiters** (`$(`, `${`) are punctuation while the shell's `${VAR}` is a config variable throughout (P8 asks for the same everywhere).
8. **Pylance**: decorators show function/class colour, builtins show user-function colour, class attributes are plain, builtin classes show user-type colour. All have modifiers Rosin doesn't style yet (`decorator`, `builtin`, `classMember`).
9. **rust-analyzer**: `const` and `static` items are plain (token types `const`, `static` have no rules).
10. **C++ operator overloads and conversion operators** show keyword colour on the name.

## 6. Limits (proven)

165 results across 78 groups, each with computed proof: the component shares its exact scope stack, or semantic type and modifiers, with a component
of a different meaning. Full table: `A1-appendix-limits.md`. The ones a reader will notice:

| Mode | What you see | Proof |
|---|---|---|
| T, C | `& * ~ ^ |` quiet, not hazard | `* / % + - ~ & | ^` all get exactly `keyword.operator.c`; the C++ grammar does separate them |
| S clangd | every operator quiet, including C++ bitwise, `!`, `?`, `new`, `delete` | clangd sends type `operator` with no kind modifier, overriding correct grammar scopes |
| T, C/C++ | struct/enum tags, typedef names at definition, member declarations, enum members, labels plain | no scope beyond `meta.block` |
| S cpptools | library functions, `uint8_t`/`size_t`, `const` globals, file-scope statics | cpptools legend has no `defaultLibrary`/`readonly`; marks them `type`/`global` |
| S clangd | file-scope `static` variables show global colour | marked `fileScope` without `static` |
| S rust-analyzer | `pub`, `mut`, `&` borrow: keyword/quiet | sent as plain `keyword`/`operator` |
| T, YAML | dates are strings | `string.unquoted.plain.out.yaml` |
| T, Rust | `unsafe` keyword colour, `//!` comment colour | `keyword.other.rust` like `let`; `//!` is a plain line comment |
